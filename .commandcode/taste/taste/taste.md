# Taste
- Wants maximal, immersive UI: abundant animations, rich styling/shine effects, "feature-bombed" pages — plain or sparse designs are rejected as "too less". Explicitly wants a look "no one has ever created" — unprecedented/original designs, not conventional or off-the-shelf UI. Confidence: 0.9
- Prefers a single strong immersive landing page whose visual language then spreads across the whole site. Confidence: 0.7
- Likes gamified/themed experiences (game and movie themes) that users emotionally relate to, not exact copies but an original take on them. Confidence: 0.6
- Prefers multi-page sites with multiple templates and layouts over a single-page site; expects all pages to be brought up to the same redesigned quality, not just one — states it as "every single page". Confidence: 0.8
- Expects both sides of a personal site to be fully built out: the admin/internal panel used as his own operating tool, plus a separate public/non-admin experience. Not one at the expense of the other. Confidence: 0.6
- Wants real, verifiable content instead of placeholder or "bad" data — e.g. actual public repos listed with proper descriptions, data seeded from real proof, certificates/timeline pulled from real source material. Confidence: 0.9
- Zero tolerance for fabricated credentials: invented roles, clubs, papers, awards, or metrics (even ones that make the portfolio look better or fuller) destroy the site's value — "that makes its values near 0". Only assert what is in his resume/certificates or what he has explicitly told you; when unsure, ask or omit, never infer and present it as fact. Confidence: 0.9
- Wants the full breadth of what he actually provided surfaced — every internship, participation, award, and ongoing research — not a curated subset. Omitting material he handed over is treated as the work not reflecting him at all ("nothing reflects", "a joke to me"). Read his source files (`classified/`, resume PDFs, certificates) and mine them before writing page content. Confidence: 0.8
- Wants unwanted/stale content and database records cleaned out rather than left in place — including purging entries he says are false from the database and from seed data, not just from page code. Confidence: 0.7
- Prefers creating a new branch before attempting experimental or risky rework. Confidence: 0.7
- Prefers free / free-tier tooling and cost avoidance — e.g. free Groq Whisper for transcription and rotating multiple Gemini API keys to stay within free limits rather than paying. Any integration should default to a free service and only escalate on approval. Restated as a hard constraint: add nothing that costs money — when a capability would need a paid service or SDK, build his own route instead (own endpoints, ffmpeg, installable web app, webhooks). Confidence: 0.85
- Wants multiple LLM providers wired in as real, first-class options (e.g. Groq alongside Gemini) rather than a single hardcoded one, and he will hand over keys to make that happen. The model chosen must be capable and durable — something with real value that won't be deprecated/disappear "in a moment" — not a throwaway preview model. Confidence: 0.65
- Prefers varied, multi-accent color palettes over a single-hue scheme — a one-colour (e.g. all-lime/all-green) theme reads as unfinished; add secondary/tertiary accents across headings, buttons, and backgrounds. Confidence: 0.65
- Rejects internal jargon as user-facing copy: labels like "scenes" / "marks" that only make sense from the source code must be renamed to plain, self-explanatory words ("repos", "featured", "awards"). Confidence: 0.65
- Prefers short, trimmed surfaces over exhaustive dumps — cap long card lists and drop low-value entries he never uses, while keeping the full archive reachable behind a separate action. Confidence: 0.6
- Wants automation to execute end-to-end but never unsupervised on external actions: an approval queue for anything outward-facing or destructive, explicit safety/ethics guardrails, and an audit log of every action. Escalates this to a hard requirement: the gate must be enforced in code and must not be bypassable — "do not post unless I say something or press", because autonomous actions can be harmful — with an emergency stop. Treats these guardrails as the first thing to get right, above adding more features. Restated as the single hardest requirement: the restriction must be "higher" and impossible to bypass — no auto-send code path may exist at all, and a blocked action must actually refuse rather than warn. Confidence: 0.9
- Expects gaps stated plainly: if part of what he asked for was skipped or is not built yet, say so explicitly and name what's missing instead of presenting the subset as complete. Confidence: 0.6
- Cares about output/asset quality — wants the best-quality version of visual assets (e.g. full resolution, no downscaling, minimal compression, "best quality") and likes to compare several candidate options (contact sheet, numbered choices) before picking the final one. Confidence: 0.7
- Judges image crops/photos by whether the subject (himself) is clearly and flatteringly in frame — a crop that zooms past him is rejected; keep him prominent while framing the subject he asked for. Confidence: 0.6
- Prefers non-destructive local dev: when a port is already taken by another of his projects, start the app on a different free port instead of stopping/killing the other project's server. Confidence: 0.55
- Expects git state to be reported honestly: whether the work is committed, how far the branch is ahead/behind `main`, and whether it can merge/push cleanly — while leaving the actual commit/push for him to run unless he explicitly hands that over. Confidence: 0.65
- Wants work committed incrementally — "commit things one by one, single file one time": one file per commit, in dependency order, each with its own focused conventional-commit message, rather than one big drop-everything commit at the end. Confidence: 0.8
- Wants a clean checkpoint before each new phase: clear out the outstanding uncommitted work first ("commit these changes one by one files here", "first commit all then do other task"), and only then start the next chunk of building. He grants permission to proceed to the next phase only after that — "i must see all things commited that are changed here" — so `git status` must come back empty (including untracked files and edits that were already sitting uncommitted before the session), not just the files the agent itself touched. Confidence: 0.85
